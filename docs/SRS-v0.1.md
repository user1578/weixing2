## 1. 项目背景与目标

当前校园反诈工作常依赖微信群转发、人工电话联系和线下表格统计，预警、学生反馈、辅导员跟进与保卫处处置之间缺少统一状态和可追溯记录。系统以微信小程序服务学生与院系辅导员，以 Web 管理后台服务保卫处/反诈专班，统一支撑：

`预警下发 → 学生上报 / 辅导员跟进 → 保卫处核验处置 → 结案留痕`

第一版目标是跑通这条闭环，并能以真实业务数据演示预警、工单、处置和统计。第一版不引入机器学习、自动研判或复杂规则引擎。

### 1.1 范围与非目标

- 范围：学生预警与上报、辅导员学院内跟进、保卫处预警/核验/处置、反诈内容和简单自测、审计与基础统计。
- 非目标：直接对接公安/96110 自动接口、支付止付、自动建库建表、复杂算法、大模型识别、OCR、安全态势大屏。
- 预警默认以人工录入或已确认来源录入为主；“规则”仅支持来源和关键词等基础配置。

## 2. 系统总体架构

### 2.1 逻辑架构

| 层级 | 组件 | 职责 |
| --- | --- | --- |
| 客户端 | 微信小程序（学生、辅导员） | 展示本人/本学院授权数据，提交上报和跟进操作 |
| 管理端 | Web 管理后台（保卫处/反诈专班） | 预警下发、规则维护、核验处置、统计和审计查询 |
| 业务服务层 | 后续 CloudBase 云函数/服务端接口 | 身份解析、RBAC 校验、学院数据范围过滤、状态迁移、脱敏、审计写入 |
| 数据层 | 后续 CloudBase 数据库、文件存储 | 保存业务数据和证据文件元数据；本文只做逻辑设计，不创建集合 |
| 平台能力 | 微信登录、CloudBase | 小程序用户身份、云端调用及已验证的运行环境 |

### 2.2 访问原则

1. 客户端仅负责交互，不能以隐藏按钮替代权限控制。
2. 所有涉及业务数据的读写均应经过服务端鉴权；服务端从微信上下文或后台登录会话解析操作者，不信任前端传来的 `userId`、`role`、`collegeId`。
3. 服务端在查询条件、单条资源校验、状态转换和响应脱敏四处执行权限控制。
4. 关键操作采用“先校验、再写入业务记录和审计记录”的方式；后续实现应保证两者尽量原子化。

## 3. 三类角色说明

| 角色 | 使用端 | 数据范围 | 核心职责 |
| --- | --- | --- | --- |
| 学生 | 微信小程序 | 本人 | 查看个人预警/风险告知、提交上报、查看本人进度、学习和自测 |
| 院系辅导员 | 微信小程序 | 本学院 | 查看学院预警与学生上报、联系跟进、填写意见、标记重点关注、转保卫处 |
| 保卫处/反诈专班 | Web 后台 | 全校 | 预警与基础规则管理、下发预警、核验/处置/结案、统计与审计 |

角色可以在用户资料中以多角色保存，但每次接口以当前有效角色授权。学生与辅导员的学院归属以服务端的人员档案为准；保卫处角色不受学院范围限制。

## 4. 学生端功能需求

### 4.1 我的预警与风险告知

- 展示仅属于当前学生的预警列表、风险等级、提醒内容、下发时间和状态。
- 打开详情时，将预警由“已下发”更新为“已查看”（幂等操作）。
- 可从预警进入与该预警关联的上报入口；关联关系由 `sourceAlertId` 记录。
- 展示本人风险提醒、辅导员/保卫处可公开给学生的处理状态；不展示内部处置备注、其他学生信息或敏感线索来源。

### 4.2 一键上报

- 学生可提交诈骗或疑似诈骗事件，必填：诈骗类型、涉及金额、事件经过、发生时间、是否已造成损失。
- 可选：可疑账号/平台、是否仍在联系、联系方式、备注、证据附件（第一版如未实现上传，页面应明确不支持而非伪造入口）。
- 成功提交后生成一张学生上报工单，初始为“待辅导员核实”；学生可查看本人处理进度与可公开的结案结论。
- 重复提交控制：客户端可防连点；服务端按“同一学生 + 相同类型 + 相近发生时间 + 相同金额”提示可能重复，但不得静默丢弃。

### 4.3 反诈学堂与自测

- 展示已发布的真实诈骗案例与防骗知识；案例发布前必须完成去标识化。
- 学生可完成单选、多选或判断题自测，提交后展示本次得分、正确答案和解析。
- 记录学习/答题行为，供“参与反诈学习人数”统计使用；题目正确答案不得在答题前下发至客户端。

## 5. 辅导员端功能需求

### 5.1 学院看板

- 仅统计和列出当前辅导员所属学院的待处理预警、待核实学生上报、高风险/重点关注学生。
- 默认按风险等级和等待时长排序；不得通过前端参数切换到其他学院。
- 列表默认脱敏联系方式和金额，进入获授权的处置详情时才按规则展示必要信息。

### 5.2 跟进与重点关注

- 对本学院预警或学生上报创建/追加跟进记录：联系时间、联系方式、跟进意见、核实结果。
- 可将学生标记为重点关注；该标记必须说明原因、标记人和时间，并影响风险评级。
- “已跟进”只表示本次辅导员跟进完成，不能替代工单结案。

### 5.3 上报处置协作

- 辅导员核实学生上报后，填写“初步属实 / 疑似但待核 / 非涉诈或误报”等结果。
- 需要保卫处处理的，转为“待保卫处核验”，并写明转交原因。
- 无需保卫处介入的低风险咨询/误报，可按权限直接标记结案，但必须填写结案结论；该规则需在第 17 章确认。

## 6. 保卫处 Web 后台功能需求

### 6.1 预警与基础规则管理

- 创建、编辑草稿、下发和关闭预警；预警可指定一个学生并自动带出学院。
- 预警来源使用受控枚举（如 `manual`、`96110`、`campus_report`、`other`）；来源参考号仅限有权限人员查看。
- 规则第一版仅维护启用状态、来源、关键词、默认风险等级和说明。规则可辅助人工创建预警，不自动做复杂判定。
- 下发前校验目标学生有效、学院归属存在、内容完整；下发后记录操作者和时间。

### 6.2 工单核验与处置

- 提供“待保卫处核验”“处置中”“已结案”队列。
- 核验时记录核验结论；进入处置时记录处置措施、责任人和下一步计划；结案时记录最终结论、确认损失金额和结案时间。
- 每次操作追加一条处置记录，禁止通过覆盖旧记录抹去历史。

### 6.3 统计与审计

- 支持按日期、学院、诈骗类型和风险等级筛选基础统计。
- 支持按资源、操作者、时间和操作类型查询审计记录；审计详情按权限脱敏。

## 7. 核心业务流程

### 7.1 预警闭环

1. 保卫处创建预警（待下发），选择来源、目标学生、内容和风险等级。
2. 保卫处下发后，学生在小程序看到“已下发”的风险提醒；首次打开更新为“已查看”。
3. 学生可基于该预警提交关联上报；也可独立上报。辅导员可对预警或上报创建跟进记录。
4. 如需升级，辅导员转交保卫处；保卫处核验、处置并结案。
5. 预警在关联事项完成或确认无需继续关注后关闭。所有下发、查看、跟进、转交、核验、处置和结案动作写入审计记录。

### 7.2 学生上报闭环

1. 学生提交上报，系统写入学院快照、初始风险等级和“待辅导员核实”。
2. 本学院辅导员联系/核实，补充跟进意见，并决定转保卫处或按授权直接结案。
3. 保卫处核验属实后进入处置中；处置完成后结案。学生只看到适合公开的进度和结论摘要。

### 9.2 服务端强制规则

- 学生请求固定以会话身份对应的 `userId` 过滤，拒绝任何前端指定他人 ID 的访问。
- 辅导员每次读取或写入前，比对资源的 `collegeId` 与服务端人员档案的 `collegeId`；不匹配直接拒绝并审计。
- 保卫处角色可跨学院，但高敏感明细、导出和权限变更应额外审计。
- 角色、学院归属、用户状态由保卫处授权管理员维护；普通客户端不能自行修改。
- 业务状态迁移必须在服务端检查当前状态、操作者角色和必填处置字段，防止跳过核验直接结案。

## 10. 状态机设计

状态名称采用可展示的中文含义，存储值可使用下表中的英文枚举。历史状态不覆盖，以审计/跟进/处置记录补充。

### 10.1 预警状态机

`待下发(pending_dispatch) → 已下发(sent) → 已查看(viewed) → 跟进中(following_up) → 已关闭(closed)`

- 保卫处创建：进入“待下发”；仅保卫处可下发或关闭。
- 学生首次打开：`已下发 → 已查看`；重复打开不重复变更。
- 辅导员开始跟进或关联上报开始处理：`已下发/已查看 → 跟进中`。
- 关联事项结案，或保卫处确认无需继续关注：`已下发/已查看/跟进中 → 已关闭`，必须填写关闭原因。
- 学生提交关联上报不会自动关闭预警。

### 10.2 学生上报工单状态机

`待辅导员核实(pending_counselor_verify) → 待保卫处核验(pending_security_verify) → 处置中(in_process) → 已结案(closed)`

- 学生提交：进入“待辅导员核实”。
- 本学院辅导员核实并转交：进入“待保卫处核验”，转交原因必填。
- 保卫处核验属实或需要行动：进入“处置中”。
- 保卫处完成处置：进入“已结案”，最终结论和确认损失金额必填。
- 对明确误报、纯咨询或无需保卫处介入的低风险事件，辅导员可从“待辅导员核实”直接结案；需填写核实结论和结案摘要。是否保留该权限需第 17 章确认。
- “补充信息”不另设状态：辅导员/保卫处以追加记录要求补充，工单仍停留在当前责任方状态，避免状态膨胀。

### 10.3 辅导员跟进状态机

`待跟进(pending) → 跟进中(in_progress) → 已完成(completed)`

- 预警下发或上报进入本学院队列时创建/提示“待跟进”。
- 辅导员首次记录联系行为：进入“跟进中”。
- 填写跟进意见、核实结果，并完成转交或本阶段处理：进入“已完成”。
- `focusFlag` 是独立布尔标记，不作为状态；可在任一状态设置，但须填原因。

### 10.4 保卫处处置状态机

`待核验(pending_verify) → 处置中(in_process) → 已结案(closed)`

- 转交保卫处后进入“待核验”。
- 保卫处确认需行动时进入“处置中”，至少记录处置措施或下一步计划。
- 处置完成进入“已结案”；若核验为误报/无需处置，可由“待核验”直接结案，但必须记录核验结论。
- 每次核验、处置、结案均新增一条 `SecurityDisposition`，工单只保存当前汇总状态。

## 11. 风险评级规则

第一版使用固定、可解释、可直接编码的优先级规则。风险等级仅有 `low`（低）、`medium`（中）、`high`（高）；每次提交、预警下发、辅导员重点标记或关键字段更新后重新计算并记录触发原因。

### 11.1 输入因素

- `hasLoss`：是否已产生经济损失。
- `involvedAmount`：涉及/确认金额。
- `stillContacting`：是否仍与可疑方联系。
- `fraudType`：是否属于重点类型（第一版建议：刷单返利、冒充公检法、虚假贷款、冒充客服退款）。
- `activeAlertCount30d`：近 30 天未关闭预警数量。
- `focusFlag`：辅导员是否标记重点关注。

### 11.2 判定顺序

1. **高风险**：满足任一项即为高风险：已产生损失；涉及金额不少于 5,000 元；仍在联系且命中重点诈骗类型；近 30 天未关闭预警不少于 3 次；已被重点关注且仍在联系或近 30 天未关闭预警不少于 2 次。
2. **中风险**：不满足高风险且满足任一项：涉及金额为 1–4,999.99 元；仍在联系；命中重点诈骗类型；近 30 天未关闭预警为 2 次；已被重点关注。
3. **低风险**：不满足上述条件，例如无损失、金额为 0、未持续联系、无重点类型和重复预警的咨询或提醒。

金额使用人民币元，`0` 表示未涉及或未知损失但仍须如实填写。阈值和重点类型由保卫处配置，但任何改动都应记录审计；第一版不使用模型分数或概率。

## 14. 操作审计与留痕规则

必须审计的动作包括：登录失败/角色拒绝、预警创建与下发、预警阅读、学生上报创建、敏感信息查看、辅导员跟进与重点标记、工单转交、保卫处核验/处置/结案、规则变更、内容发布、数据导出和用户角色/学院变更。

- 审计记录至少保存操作者、角色、时间、资源、动作、结果、请求追踪号和必要的状态前后摘要。
- 跟进记录和处置记录采用追加方式；已结案记录不得物理删除。若需更正，追加“更正”记录并保留原记录。
- 读取高敏感字段和导出应记录访问目的（如系统支持）与结果；审计记录本身仅允许保卫处授权角色查询。
- 审计快照只保存追溯所需字段，敏感值按脱敏或受控存储处理，避免复制完整隐私内容。

## 15. 异常场景与边界条件

| 场景 | 处理原则 |
| --- | --- |
| 学生未绑定学院或身份不一致 | 禁止下发/上报入队，提示联系管理员；保留失败审计 |
| 辅导员访问其他学院资源 | 服务端拒绝，不以“空列表”掩盖权限问题，并记录拒绝审计 |
| 目标学生已停用/毕业 | 不允许新下发；历史预警保留，按数据保留规则处理 |
| 重复点击提交或网络重试 | 客户端防连点，服务端使用幂等键或重复提示，避免重复工单 |
| 状态被并发修改 | 使用版本号/更新时间校验；冲突时返回最新状态并要求刷新后重试 |
| 金额未知或无损失 | 金额允许为 `0`，`hasLoss=false`；不得以空字符串代替数值 |
| 预警关联多个上报 | 预警可关联首个主工单并在关联列表保留多个记录；关闭时检查未结案关联事项 |
| 附件上传失败或含敏感信息 | 第一版未实现前不收集；后续实现需病毒/格式/访问控制校验，不允许附件公开链接 |
| 学生不再响应 | 辅导员持续记录联系尝试；达到学校规定时限后转保卫处或标记待持续跟进 |
| 小程序通知未订阅 | 以应用内未读预警为准；订阅消息仅作可选增强，不能作为唯一通知依据 |
| 误报或恶意上报 | 保留工单和核验结论；不得物理删除，必要时限制频繁提交并审计 |

## 17. 需要用户确认的问题

以下问题会直接影响后续数据模型、权限实现或业务状态，不涉及颜色、布局等界面细节：

1. **人员与学院主数据来源**：学生、辅导员、学院和毕业/调院状态由谁维护？是否已有可导入的学号—学院—辅导员映射？
2. **身份绑定方式**：学生首次进入小程序如何与学号/姓名档案绑定？辅导员是否使用同一小程序，保卫处 Web 后台采用何种登录方式？
3. **辅导员结案权限**：是否允许辅导员对“误报/咨询且无风险”的上报直接结案，还是所有学生上报均必须转保卫处？本稿暂定前者可直接结案且必须留痕。
4. **预警来源范围**：第一版是否只允许人工录入、96110 和校内上报三类来源？“96110”信息是人工录入还是未来接口同步？
5. **风险规则阈值**：高风险金额阈值暂定 5,000 元、重复预警窗口暂定 30 天；是否符合学校的实际处置规范？重点诈骗类型名单是否需要调整？
6. **处置时限（SLA）**：高风险预警/工单的辅导员首次跟进时限暂定 48 小时，仅用于统计；是否需要改为学校规定的时限并配置超时升级？
7. **损失金额口径**：统计以保卫处结案确认金额为准；学生上报的“涉及金额”仅用于风险研判。该口径是否认可？
8. **敏感数据保留与导出**：联系方式、账号、附件和审计记录的保留期限、是否允许导出、谁可导出，需依据学校制度确定。
9. **学生可见结论**：保卫处处置记录中哪些字段可以对学生公开（例如“已核验，已完成安全提醒”），哪些必须始终内部可见？
